# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository at a glance

`spksrc` is SynoCommunity's cross-compilation and packaging framework for Synology DSM packages. Most of the repo is Makefile-driven: package recipes declare metadata and dependencies, while shared `mk/*.mk` fragments implement the staged build pipeline and the supported architecture/toolchain matrix.

## Build model

- `spk/<pkg>`: final SPK package recipes. These usually define `SPK_NAME`, version/revision, maintainer metadata, service settings, package dependencies, and then include `../../mk/spksrc.spk.mk`.
- `cross/<pkg>`: cross-compiled libraries/apps used by packages. These recipes define `PKG_*` metadata, configure flags, and then include `../../mk/spksrc.cross-cc.mk`.
- `native/<pkg>`: host-side tools built for the build machine.
- `toolchain/syno-*`: Synology toolchain definitions for each arch/version combination.
- `toolkit/`: SDK/toolkit builders and helper toolchains.
- `kernel/`: kernel-related builds.
- `diyspk/`: hand-written DIY package recipes.
- `mk/`: shared build logic. `spksrc.common.mk` computes toolchain/arch lists, logging, and parallelism; `spksrc.cross-cc.mk`, `spksrc.spk.mk`, and `spksrc.tc.mk` define the build flows for cross packages, SPKs, and toolchains; `spksrc.supported.mk` fans targets out across supported or latest arch sets.

The common build pipeline is `download -> checksum -> extract -> patch -> configure -> compile -> install -> plist`. Per-package and per-toolchain makefiles hook into that pipeline through the shared includes.

Generated artifacts live under per-recipe `work*`, `build*`, `status*`, `publish*`, and `wheel*` directories. These are intentionally ignored by git.

`local.mk` is generated by `make setup` and holds local defaults such as `DEFAULT_TC`, publish settings, and other site-specific configuration.

## Common commands

Run these from the repository root unless noted otherwise.

- `make setup` — create `local.mk` and seed the default DSM/toolchain configuration.
- `make setup-synocommunity` — same as `setup`, but fills the SynoCommunity publish/distributor defaults.
- `make all-supported` — build every supported arch/toolchain combination.
- `make all-latest` — build only the latest toolchain per arch.
- `make lint` — run the repository lint entry point.
- `make jsonlint` — validate the JSON-like package metadata files under `spk/`.
- `make test-all` — run the framework test suite defined in `mk/spksrc.test-rules.mk`.
- `make test-<target>` — run one named test target directly. `make test` requires an additional goal and is not useful by itself.
- `make test-info` — print the supported arch strings that can be used for single-test targets.
- `make test-toolchain-<supported-arch>` — run one toolchain test case for a single `arch-version` entry from `make test-info`.
- `make -C spk/<pkg> all-supported` — build one SPK across all supported archs.
- `make -C spk/<pkg> ARCH=<arch> TCVERSION=<version>` — build one SPK for a single arch/toolchain pair.
- `make -C cross/<pkg>` — build one cross dependency or library.
- `make -C native/<pkg>` — build one native host helper.
- `make -C toolchain/<name>` — build one toolchain recipe.

For a full development environment, follow the setup described in `README.md`: Debian 13 is the recommended base, and the Docker-based flow is for Linux/macOS rather than Windows file systems.

## Navigation and change boundaries

When changing build behavior, start in the recipe that owns the behavior and then follow the include chain into `mk/`:

- package metadata/service packaging problems usually live in `spk/<pkg>` and `mk/spksrc.spk.mk`
- dependency or build-system issues usually live in `cross/<pkg>` and `mk/spksrc.cross-cc.mk`
- toolchain generation issues usually live in `toolchain/syno-*` and `mk/spksrc.tc.mk`
- architecture selection issues usually live in `mk/spksrc.common.mk`, `mk/spksrc.archs.mk`, and `mk/spksrc.supported.mk`

`SUPPORTED_ARCHS` and `LATEST_ARCHS` are computed from installed toolchains, the default toolchain in `local.mk`, and the generic/deprecated arch filters. They are not hard-coded lists.
